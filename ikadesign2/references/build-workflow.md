# 根据设计系统实现前端

## 目标与边界

使用 `design.md` 实现符合读者任务的真实页面。品牌一致不等于布局一致。不同页面可以采用不同结构，但必须共享适用的视觉规则和原语。

不要建立额外的主题系统。不要安装与当前任务无关的组件。不要部署、提交、推送或访问用户未授权的外部服务。

本流程是 `ikadesign2` 技能的生成模式。检查记录、机械自检、问题分类和停止规则见 [检查与回写](review-loop.md)。

## 1. 解析 design.md 与任务

1. 读取用户指定的 `design.md`。
2. 没有指定时，使用项目已有的 `design.md`。
3. 检查 `design.md` 是否覆盖当前页面类型和主题。
4. 整理目标读者、主要任务、真实内容和必要操作。
5. 区分用户要求、`design.md` 约束和本次实现决策。

页面的功能、字段和数据来自任务需求和代码，不来自 `design.md`。`design.md` 只决定它们如何呈现。

没有 `design.md` 时，不要假装按它生成。返回 [技能入口](../SKILL.md) 的提取或创建流程。

`design.md` 只覆盖部分任务时，沿用已确认部分。对缺失部分作最小实现决策，并在交付中列出。若缺失信息会改变品牌方向、商业含义或授权范围，则合并提问。不因局部缺口回到创建流程。

保留用户提供的事实、公式、单位、限定词和素材。不要补造客户评价、统计数据、产品能力、价格或推荐结论。

## 2. 检查宿主项目

检查实际框架、路由、样式入口、字体、主题、组件 API 和启动方式。保留现有结构与无关修改。

根据 `design.md` 选择以下一种实现方式：

### 项目已有实现

复用已存在的 token、组件、布局和主题入口。读取相关组件的真实属性与用例。不要仅凭组件名称猜测 API。

### design.md 引用独立样式表

确认资源地址可访问且响应为 CSS。按 `design.md` 加载一次。使用第 5 章列出的公开原语和扩展命名空间。不猜测未列出的名称，不覆盖内部选择器。

公开原语足够时，不必把整份 CSS 读入上下文。遇到加载、优先级、主题或状态问题时，可以读取相关实现定位原因。

远程资源受网络、隐私或项目策略限制时，使用获准的本地副本或明确的替代实现。记录差异，不使用失效链接或无权使用的资产。

### design.md 只有设计值

在当前项目的既有样式入口落实所需 token 和组件变体。没有既有入口时，选择最小的共享样式文件。

区分基础值、语义角色和组件用途。只实现当前页面需要的规则。不要在各页面复制颜色、字号和间距声明。

将新建 token 的真实名称和路径回写到 `design.md`。没有权限修改 `design.md` 时，在交付中提供具体修订建议。

## 3. 确定页面结构

先列出内容和操作，再选择布局。

在内部确定：

- 页面类型及其适用规则。
- 首屏必须出现的答案、操作或证据。
- 主要区域的顺序与宽度关系。
- 移动布局中的重排方式。
- 必要的交互和数据状态。

内容支持多种明显不同的结构时，比较两种构图。选择最有利于读者任务的结构。不要求为明确的既有布局制造备选方案。

不要把所有任务变成居中标题加卡片网格。也不要把 Vercel 的黑白、字体、禁用渐变或隐藏主题切换等品牌选择当作通用要求。

不要在用户界面展示设计推理、规则编号或检查记录。

## 4. 实现页面

按以下顺序实现：

1. 语义结构和内容顺序。
2. 共享布局与响应式行为。
3. 真实组件及其变体。
4. 字体、颜色、间距和媒体。
5. 必要交互、状态和可访问性。

使用 `design.md` 公开的原语。新布局可以组合原语，但不能通过页面级覆盖悄悄改变它们的含义。

缺少布局方式时，在 `design.md` 声明的扩展命名空间内增加最小的页面布局样式。缺少复用机制时，扩展实际拥有该规则的组件或样式入口。不要建立平行的命名体系。

有后端或真实数据要求时，接入实际行为。视觉示例允许固定示例数据，但必须在任务范围中明确其性质。不要把无效按钮、虚假成功状态或静态演示声称为完整功能。

使用原生语义、可见焦点、可访问名称和合理对比度。不要通过隐藏溢出掩盖布局错误。

## 5. 运行并检查

使用项目已有命令启动真实页面。通过现有浏览器或预览工具打开目标路由。

固定本次内容、视口、主题和 `design.md` 版本。先检查桌面，再检查窄屏。项目已有断点时沿用它们；否则可用 1440 × 900 与 390 × 844 作为初始检查视口，而不是设计规则。

先执行 [检查与回写](review-loop.md) 的机械自检，再按其人工检查顺序检查首屏和全页。按需检查已支持主题、长文本、大数字、加载、空、错误、禁用及键盘操作。只有与页面有关的状态才需要构造。

用截图检查外观。用 DOM、计算样式和实际操作检查结构与行为。模型自评只能辅助检查，不能替代渲染，也不能代表用户批准。

没有运行或浏览器工具时，完成可执行的代码与引用检查。明确报告“未做渲染检查”或“交互未检查”。不要把代码审查称为视觉通过。

## 6. 修复并回写

按 [检查与回写](review-loop.md) 的问题分类记录每个发现。按其停止规则决定修复范围和复查方式。

先修复当前页面，再处理可复用的规则。页面修复与规则回写不能互相替代。

明确用户反馈与模型建议的区别。方向性变更需要用户取舍时，提出建议而不宣称已批准。

检查记录按 [检查与回写](review-loop.md) 的格式写入现有任务记录。若修改了带 `version` 字段的 `design.md`，更新该字段。不要维护互相冲突的文档与代码数值副本。

## 完成条件与交付

- 已实现本次要求的内容和行为。
- 使用的组件、token 和资源均可解析。
- 已修复停止规则范围内的违反项。
- 已处理可复用的规则缺失，或给出明确的未批准建议。
- 检查记录与实际执行范围一致。

交付页面路径、启动或访问方式、`design.md` 变更及检查限制。仅在实际运行后报告运行成功。若工具或授权阻止进一步检查，说明阻碍和已完成部分，不声称闭环已完成。
